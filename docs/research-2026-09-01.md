# Agent bus 조사 및 기초 검증 기록

관측 시각: 2026-09-01 15:10~17:16 KST

이 문서는 그 시점의 CLI, 세션, 소스 상태를 기록합니다. 이후 버전이나 세션 상태는
다시 확인해야 합니다.

> 구현 상태 안내: 이 문서의 커스텀 대화 화면·통합 승인 화면·`notify_agent` 관련
> 결론은 2026-09-02의 [ADR 0002](adr/0002-native-provider-tui-wrapper.md)로
> 대체됐습니다. 아래 내용은 당시 조사와 실패 이력을 보존한 기록입니다.

## 목표

독립적인 Codex/Claude 작업세션을 사용자가 한 화면에서 발견하고 다음 동작을 직접
제어할 수 있게 합니다.

- Codex 1이 Claude 3에 질문하고 답을 받습니다.
- Codex 1이 Codex 2에 적대 검토를 요청하고 답을 받습니다.
- 제공자 차이는 `list_agents`, `ask_agent`, `notify_agent` 뒤로 숨깁니다.
- 기존 TUI에 키 입력을 주입하지 않고 공식 또는 로컬 메시징 전송을 사용합니다.
- 자율적인 통합세션 LLM을 두지 않고 사용자가 세션 생성, 최초 지시, 중요한 승인을
  담당합니다.
- 작업세션의 worktree·구현·검증 생명주기는 각 세션의 작업 스킬에 맡깁니다.
- 에이전트 답변을 자동 재전달하지 않아 한 요청이 무한 대화로 번지지 않게 합니다.
- 통합 화면의 세션 카탈로그와 통신 가능한 에이전트 목록을 분리합니다. 유휴
  `Sleeping` 세션은 화면에는 남지만 버스 라우팅에서는 빠지고, 사용자가 상세
  화면에 들어가 resume했을 때 다시 등록됩니다.
- 통합 TUI는 세션 실행기의 부모 프로세스가 아니라 백그라운드 서비스의
  재접속 가능한 클라이언트로 둡니다. 화면을 종료하고 다시 실행해도 같은 세션과
  transcript가 보여야 하며, 명시적인 stop만 작업세션을 종료합니다.

## 현재 환경에서 확인한 사실

- Node.js `24.15.0`, npm `11.12.1`, Codex CLI `0.152.0`, Claude Code
  `2.1.252`입니다.
- `codex app-server generate-ts --experimental`로 현재 설치본의 타입을 생성해
  `initialize`, `thread/start`, `turn/start`, `turn/completed` 계약을 확인했습니다.
- [Codex App Server 공식 문서](https://learn.chatgpt.com/docs/app-server)는 stdio
  JSONL, WebSocket, WebSocket-over-Unix-socket 전송과
  `initialize` → `initialized` 생명주기를 설명합니다. WebSocket 전송은 문서상
  실험적이므로 버전 고정과 시작 시 능력 검사가 필요합니다.
- stdio와 WebSocket-over-Unix-socket 모두 모델 턴 없이 `initialize` 왕복에
  성공했습니다. Unix 경로는 `/run/user/1001`에서 성공했고 `/tmp`에서는
  `Operation not permitted (os error 1)`로 실패했습니다.
- [Claude cross-session messaging 공식 문서](https://code.claude.com/docs/en/cross-session-messaging)에
  따르면 같은 머신 메시지는 세션별 Unix 소켓으로 전달되고, 받은 메시지는 일반
  프롬프트와 같이 사용량을 소비합니다. 동료 메시지는 사람의 승인으로 취급되지
  않습니다.
- [Claude Channels 공식 문서](https://code.claude.com/docs/en/channels)는
  `claude/channel` 능력과 `notifications/claude/channel` 푸시를 제공합니다. 다만
  개발 채널 플래그로 시작한 세션만 참여하므로 이미 실행 중인 일반 세션의 자동
  발견 요구에는 맞지 않습니다.
- `claude agents --json`과 `~/.claude/sessions`를 읽기 전용으로 비교했을 때
  세 개의 live 세션과 `/run/user/1001/cc-socks/<PID>.sock` 경로를 확인했습니다.
  이 세션들에는 메시지를 보내지 않았습니다.
- 현재 실제 transcript의 wrapper에는 `from`, `from-session`, `hop-chain`,
  `from-name`, `from-mode` 속성이 관측됐습니다. 이 외부 peer frame은 공개된 안정
  API가 아니므로 전용 테스트 세션에서 현재 버전을 검증하기 전에는 사용하지
  않습니다.

실패 사례를 찾는 참고 자료로만 사용합니다.

## 기초 통신 검증 결과

1. Codex stdio JSONL: `initialize` 응답 성공, 모델 턴 없음.
2. Codex WebSocket-over-Unix: HTTP Upgrade `101`과 `initialize` 응답 성공,
   모델 턴 없음.
3. Codex 실제 모델 턴: 전용 ephemeral thread, 승인 정책 `never`, read-only
   sandbox에서 `PING → PONG`, 턴 상태 `completed` 확인.
4. Claude 형태의 가짜 peer 두 개: 대상 소켓 전달과 요청자 소켓 역접속 답장 성공.
   요청/답장 `msg_id`는 달랐고 `in_reply_to`는 없었습니다.
5. 저장소 브로커: 5개 테스트 성공. 목록, ask, notify, `0600`, 타임아웃,
   직렬화, 기존 소켓 보존을 검사했습니다.

이후 Codex 프로토타입과 관리 TUI 테스트를 추가해 현재 전체 격리 테스트는 36개입니다. 실제
TUI queue는 대상의 기존 YOLO 정책을 유지한다는 점을 관측했으므로, queue 어댑터는
read-only 대상이 아니면 전송을 거부합니다. 별도 App Server에서 기존 세션을
ephemeral read-only thread로 분기하는 shadow 왕복은 실제 `SHADOW_PONG` 응답까지
확인했습니다. 두 경로 모두 한 요청을 한 턴으로 끝내며 응답을 자동 재전달하지
않습니다.

추가 permission probe에서는 외부 MCP 세 개를 이름별로 비활성화한 뒤
`workspace-write + on-request + user reviewer`인 ephemeral Codex thread를
사용했습니다. `probe.txt` 생성과 삭제가 모두 승인 요청 없이 완료됐습니다. 따라서
Codex 기본 workspace-write 정책만으로는 “일반 수정은 자동, workspace 내부의
파괴적 변경만 직접 사용자 승인”을 보장할 수 없습니다. 별도의 명령/파일변경 가드가
실측되기 전에는 통합 화면의 승인 경계가 완성됐다고 판정하지 않습니다.

관리형 TUI에서는 전용 Unix 소켓 App Server를 화면 프로세스와 분리해 실행하고,
durable read-only thread `01a05bf1-6de8-7273-9b97-96c53b744ecb`에 두 메시지를 직접
보냈습니다. 각각 `READY MANAGED`, `READY MANAGED TWO` 한 응답으로 끝났습니다.
TUI를 종료한 뒤 백그라운드 프로세스가 같은 PID로 살아 있음을 확인했고, TUI를 다시
실행해 같은 thread ID와 네 메시지를 재열었습니다. Codex의 이후 `thread/list`는
생성 때 받은 `threadSource=agent-bus`를 `null`로 반환했으므로, 화면이 만든 thread
ID는 사용자 전용 runtime 카탈로그에 기록하고 실제 목록 상태와 결합합니다.

[Codex Hooks 공식 문서](https://learn.chatgpt.com/docs/hooks)에 따르면 동기
`PreToolUse` 훅은 `Bash`와 `apply_patch`를 실행 전에 관찰하고 차단할 수 있습니다.
다만 `permissionDecision: "ask"`는 현재 지원되지 않고 일부 특수 도구는 기본 훅
경로를 선택적으로 우회할 수 있습니다. 따라서 관리형 세션에서는 외부 도구를 끄고,
위험 호출을 찾은 훅이 통합 TUI의 직접 입력을 기다린 뒤 `allow` 또는 `deny`를
반환하는 별도 경로를 검증해야 합니다.

설치된 Codex `rust-v0.152.0` 소스와 임시 App Server를 추가로 대조했습니다.
`permissionDecision: "ask"`는 스키마에는 있지만 출력 파서에서 지원하지 않으므로,
훅이 자체 Unix 소켓에서 포그라운드 결정을 기다린 뒤 `deny` 또는 무출력 성공을
반환하도록 구현했습니다. `environments: []`는 로컬 도구를 포함한 실행 환경을
명시적으로 비우므로 관리형 작업 thread에서는 이 필드를 생략해야 했습니다. 또한
App Server 프로세스의 훅 신뢰 우회 플래그만으로는 thread 실행 엔진에 세션 플래그
훅이 들어가지 않아 `thread/start.config.bypass_hook_trust=true`를 함께 지정해야
했습니다.

최종 임시 검증에서는 기존 백그라운드와 별도인 workspace-write thread가 임시 표식
파일에 `rm -f`를 요청했습니다. `hook/started`와 sessionFlags 소스의
`hook/completed(status=blocked)`를 받았고, 차단 이유는 포그라운드 승인 화면 부재였습니다.
명령 실행 item은 생성되지 않았으며 표식 파일과 `~/.codex/config.toml` 해시는
그대로였습니다. 이 시점의 결과는 거부 경로의 실행 전 차단만 증명했고, 실제 통합
TUI에서 사람이 `y`를 눌러 허용하는 경로는 아직 검증하지 않았습니다.

2026-09-02에는 설치된 Codex 0.152.0 타입과 App Server 계약을 대조해 직접 승인
성공 경로를 연결했습니다. 관리 훅의 `session_id`, `turn_id`, `tool_use_id`를 App
Server 요청의 `threadId`, `turnId`, `itemId`와 맞추고, Bash는 명령과 작업 디렉터리도
일치할 때만 15초짜리 토큰을 한 번 소비합니다. file change도 같은 item만 허용합니다.
불일치, 재사용, 만료, 상관관계를 만들 수 없는 권한확대 요청은 모두 거부하는 격리
테스트를 포함해 당시 전체 55개가 통과했습니다.

첫 실사용 재검증에서는 새 thread가 생성된 직후 App Server의 `thread/list` 반영보다
화면 새로고침이 먼저 실행됐고, 화면이 잠깐 비어 있는 활성 목록을 근거로 카탈로그
ID를 삭제했습니다. 그 결과 동일한 thread ID의 승인 훅도 “관리 카탈로그에 없는
세션”으로 거부됐습니다. 활성 목록에서 일시적으로 빠진 ID는 유지하고 실제 archived
목록에서 종료가 확인된 ID만 정리하도록 수정했으며, 이 순서를 재현하는 회귀 테스트를
추가해 전체 56개가 통과했습니다.

수정된 TUI의 실사용 재검증에서는 thread
`01a05f81-3332-73c0-920b-370e2075f881`가 카탈로그에 유지됐고, 사용자가 승인
화면에서 직접 `y`를 눌렀습니다. 이어 `rm -- .agent-bus-approval-probe && test ! -e
.agent-bus-approval-probe`가 종료코드 0으로 완료됐으며 별도 읽기 전용 확인에서도
파일 부재가 확인됐습니다. 이로써 화면 부재 시 차단, 직접 거부, 직접 승인 성공의
세 경로를 모두 실측했습니다.

같은 세션의 상세 화면 진입이 느리다는 피드백 뒤 App Server 호출을 계측했습니다.
기존 `thread/list`는 필터 없이 최대 100개를 JSONL 보정까지 수행해 한 번에
714~835ms가 걸렸고, 상세 진입 한 번에 이를 두 번 호출했습니다. 현재 workspace의
상태 DB만 조회하도록 바꾸자 목록은 2.93ms, 이미 선택된 세션 ID로 transcript만
조회하는 상세 진입은 0.97ms로 측정됐습니다. 화면도 조회 완료 전에 즉시 상세 보기로
전환하도록 바꿨으며 당시 전체 격리 테스트 58개가 통과했습니다.

2026-09-02에는 장기 transcript가 상세 진입과 메모리를 계속 키우지 않도록 최근
thread item 최대 100개를 역순 페이지로 요청한 뒤 대화 메시지는 시간순으로 표시하도록 바꿨습니다. 자동
갱신은 이 최신 페이지로 캐시를 교체하고, 사용자가 `PageUp`을 누른 경우에만 이전
페이지를 앞에 합칩니다. 메시지 ID 중복 제거, 같은 thread의 새 메시지 갱신과 과거
페이지 요청 직렬화, 명시적으로 펼친 과거 이력의 후속 갱신 보존을 회귀 테스트로
고정했습니다. App Server 초기화에서는 화면이 사용하지 않는 고빈도 delta 알림을
opt-out하고, 화면 이벤트는 25ms debounce, 동일 frame 출력 생략, 5초 안전 폴링으로
조정했습니다. 구문 검사, 격리 테스트 62개와 가짜 에이전트 데모가 통과했습니다.

4번은 Unix 프레이밍과 역방향 라우팅만 증명합니다. 실제 Claude가 현재 wrapper를
받아 모델 턴을 시작하고 답장한다는 증거가 아닙니다.

## 구현 순서와 중단 게이트

1. 완료: 제공자 독립 브로커와 가짜 에이전트 왕복.
2. 완료: 현재 생성 타입을 사용한 Codex App Server 클라이언트와 read-only shadow
   어댑터. 전용 thread의 한 번의 `ping → pong` 모델 턴까지 통과했습니다.
3. 완료: Codex 통합 화면. 실제 관리 thread 하나에서 커서 이동, 목록↔세션 왕복,
   새 세션, 화면 분리, 재실행 후 transcript 복구를 검증했습니다. 이름 변경과
   명시적 stop은 가짜 백엔드 회귀 테스트로 검증했습니다.
4. 완료: Codex 관리형 작업세션의 조사·workspace 수정·테스트 자동 실행과
   중요 작업 가드의 화면 부재 시 차단을 구현·검증했습니다. App Server 승인 요청은
   화면에서 직접 승인한 훅 요청과 정확히 대응할 때만 한 번 해제하고 공개 버스
   RPC에는 승인 기능을 노출하지 않습니다. 실제 사용자의 승인/거부 키 입력도
   검증했습니다.
5. 완료: Codex 작업세션 여러 개의 생성, 상태, 이름 변경, 종료, 전환을 검증했습니다.
6. 완료: Claude 2.1.258의 공식 background session CLI를 실제 임시 세션으로
   생성·후속 입력·종료까지 검증하고 같은 상태 모델에 연결했습니다.
7. 완료: Codex와 Claude 원본을 각각 ephemeral shadow로 분기해 한 요청·한 응답,
   대상별 직렬화, 타임아웃, 자동 전달 금지를 검증했습니다.

통합 화면은 세션을 대신 관리하는 LLM이 아닙니다. 사용자가 작업세션을 만들고
`/issue-loop #127번 이슈 확인하고 처리해줘` 같은 최초 지시를 보내며, 화면은 그
세션들의 상태와 직접 승인 지점을 모아 보여주는 사람 중심 control plane입니다.

이 단계에서는 실제 Claude 모델 검증 전이었으므로 “Codex/Claude 통신 완료”라고
판정하지 않았습니다. 아래 2026-09-02 기록이 그 후속 검증입니다.

## 2026-09-02 전역 통합 및 실제 Claude 검증

관측 시점의 설치본은 Codex CLI 0.152.0, Claude Code 2.1.258, Node.js 24.15.0입니다.
[Claude Agent View 공식 문서](https://code.claude.com/docs/en/agent-view)는 사용자별
supervisor가 여러 프로젝트의 background session을 유지하며 view를 닫아도 작업이
계속된다고 설명합니다. [Claude CLI 공식 문서](https://code.claude.com/docs/en/cli-usage)의
`agents --json`, `--background`, `--resume`, `attach`, `logs`, `stop`, `rm` 계약을
어댑터의 안정 경계로 사용했습니다. 비공개 `control.sock` 프레임은 전송 구현에
사용하지 않았습니다.

전역 daemon은 workspace registry, Codex App Server, Claude CLI adapter, 승인
대기열, peer broker를 소유합니다. 각 TUI는 같은 `0600` control socket에 붙고,
빈 프로젝트 등록과 세션 상태·순서·승인 변경을 event broadcast로 즉시 받습니다.
프로젝트 접기와 커서는 화면별 로컬 상태입니다. runtime과 영속 파일은 각각
당시 이름 기준으로 `$XDG_RUNTIME_DIR/agent-bus`, `$XDG_STATE_HOME/agent-bus`로 분리했습니다.

실제 Claude 검증에서 최초 `--background --resume`은 상태가 idle이어도 worker가
살아 있으면 새 session copy를 만들었습니다. 구현은 반환 ID 불일치를 감지해 원본
ID로 오인하지 않았습니다. 이후 idle 상태를 다시 확인하고 공식 `claude stop`으로
worker만 내린 뒤 `--background --resume <full-session-id>`를 실행하자 동일한 short
ID와 full session ID가 유지됐습니다. 최종 disposable session `e45172c0`은
`READY CLAUDE A`, 후속 `READY CLAUDE B`를 같은 conversation에서 반환했습니다.

peer 질문은 source session에 직접 넣지 않습니다. Claude는
`--print --resume <id> --fork-session --no-session-persistence --safe-mode --restricted
--strict-mcp-config --disable-slash-commands --permission-mode plan --tools ""`로 실행해
`PING SAFE` 한 응답을 받았습니다. Codex source
`01a05fc8-4b87-7152-a456-913b1da259b8`도 ephemeral read-only fork에서
`PING CODEX SAFE` 한 응답을 받았습니다. 검증 뒤 source transcript를 다시 읽었을 때
Claude는 최초/후속 네 메시지, Codex는 최초 두 메시지만 있어 shadow 요청이 원본에
섞이지 않았습니다. 모든 disposable Claude 행과 worker는 이름·cwd를 확인한 뒤
`stop`과 `rm`으로 정리했고 기존 사용자 세션에는 메시지나 신호를 보내지 않았습니다.

이 시점의 격리 테스트는 91개였고 모두 통과했습니다. 이 숫자는 이후 변경될 수
있으므로 최종 기준은 `npm run check`의 실제 출력입니다. 남은 제품 경계는 Claude
고유 권한 승인 UI입니다. 당시 agent-bus는 `Needs input`을 표시하지만 이를 대신 승인하지
않으며, 사용자가 `claude attach <id>`에서 직접 처리합니다.

최종 패키징 검증에서는 수면 상태 Claude 행을 상세 화면에서 열 때 새 프롬프트 없이
같은 full session ID를 resume하는 회귀 테스트를 추가했고, 전체 구문 검사와 94개
격리 테스트, 가짜 브로커 데모가 통과했습니다. `npm pack --dry-run`은 42개 파일,
61.5KB tarball을 구성했고 `npm link` 후 전역 `agent-bus --version`이 0.2.0을
반환했습니다. 격리된 XDG runtime/state에서 서로 다른 두 프로젝트의 TUI를 동시에
실행하자 두 번째 프로젝트 등록이 첫 번째 화면에도 revision event로 즉시 나타났고,
daemon을 종료했다가 다시 실행한 뒤에도 두 빈 프로젝트 그룹이 registry에서
복원됐습니다.

같은 날 공개 명칭을 **Wattari Gattari**, 저장소와 npm 패키지를
`wattari-gattari`, CLI를 `waga`로 변경했습니다. 새 상태 경로는
`$XDG_STATE_HOME/wattari-gattari`이며, 기존 `agent-bus`의 Codex catalog, Claude
alias, workspace registry는 최초 실행에서 원본을 남긴 채 새 경로로 복사합니다.
기존 `threadSource=agent-bus` 세션도 계속 관리 대상으로 인식합니다.
