# 스킬 실행 계획 연결

계획은 이슈루프처럼 사용자가 시작한 다단계 작업을 수행하는 에이전트가 등록합니다.
수행 에이전트가 이미 작성한 계획을 사용하므로 Waga가 별도 분류·요약 모델을 호출하지 않습니다.
일반 질문·설명·응답 종료는 계획 생성 조건이 아닙니다.

## 저장소 진입 계약

이 저장소의 `AGENTS.md`가 가리키는 지침입니다. 사용자가 허용한 다단계 로컬 코딩 작업을
시작하는 에이전트는 첫 파일 수정 전에 아래 순서를 따릅니다. 일반 질문·설명은 변하지 않습니다.

1. 시작: `waga agents --json`으로 자신의 정확한 provider 접두사 세션 ID를 확인하고,
   `waga plan <provider:session-id>`로 읽은 최근 원문 사용자 메시지의 ID를 고릅니다.
   추측한 세션 ID나 요약문의 ID를 쓰지 않습니다.
2. 인계: 계획 JSON에 원래 지시의 `messageId`와 `execution`을 담아
   `waga plan <provider:session-id> <plan.json> --execute`로 등록합니다.
   이후 같은 파일 수정을 중복 수행하지 않습니다.
3. 상태: `waga plan <provider:session-id>`로 저장된 계획·실행을 조회합니다.
   접수가 불명확해도 새 실행을 만들지 않습니다. 등록만 한 계획의 단계 변화는 같은 messageId와
   반환 revision으로 갱신하고, 인계한 계획은 실행 기록에서 상태를 읽습니다.
4. 결과: 실행 결과·검사·검토를 회수해 확인된 것과 확인하지 못한 것을 구분해 보고합니다.
   근거 없이 통과·완료라고 쓰지 않습니다.

후속 질문·답변·설명 요청은 새 작업이나 새 계획이 아닙니다. 실행이 실패해 종료된 뒤
재계획할 때는 같은 messageId·현재 revision에 `replanFrom: "종료된 실패·중단 실행 ID"`를 넣습니다.
서버가 실패 상태와 실행기 종료를 확인한 뒤 다음 revision을 저장합니다. 이전 실행의
명세·시도·실패는 그대로 남고 새 revision은 한 번만 실행됩니다. 진행 중이거나 검증을 통과한
실행을 이 방식으로 덮어쓸 수 없습니다. 사용자 승인·shipping(머지·배포·push)·기존 스킬 권한·native 소유
경계는 그대로이며, 기존 사용자 세션·provider daemon·전역 설정은 읽기 전용입니다.

Waga worker 안에서 수행 중인 작업은 계획을 다시 등록하거나 스스로를 실행으로 넘기지
않습니다. 작업이 실행기 명세에 맞지 않거나 `waga` 서비스를 쓸 수 없으면 그 사유를
"관측만 함"으로 명시하고, 실행기에 인계됐다고 주장하지 않습니다.
이 진입점은 이 저장소에만 적용되며 다른 프로젝트나 기존 외부 스킬을 자동으로 바꾸지 않습니다.

## 에이전트 등록과 갱신

`waga agents --json`에서 자신의 정확한 provider 접두사 세션 ID를 확인합니다.
`waga plan <provider:session-id>`는 최근 원문 사용자 메시지와 기존 계획·revision을 읽습니다.
처음 선택한 원문 ID를 보존하고, 후속 질문마다 새 ID로 계획을 등록하지 않습니다.

에이전트가 다음 형태의 파일을 작성하고 `waga plan <provider:session-id> <plan.json>`으로 등록합니다.
`--cwd`는 선택적인 세션 발견 필터이며 계획 대상은 정확한 세션 ID로 선택합니다.

```json
{
  "messageId": "원래 사용자 지시의 native 메시지 ID",
  "revision": 0,
  "title": "웹·TUI 세션 순서 동기화 수정",
  "skill": "issue-loop",
  "nodes": [
    { "id": "reproduce", "title": "순서 불일치 재현", "dependsOn": [], "state": "active", "evidence": [] },
    { "id": "fix", "title": "저장·조회 경로 수정", "dependsOn": ["reproduce"], "state": "pending", "evidence": [] },
    { "id": "check", "title": "웹·TUI 왕복 동기화 검사", "dependsOn": ["fix"], "state": "pending", "evidence": [] }
  ]
}
```

실제 과제에 필요한 단계와 의존 관계를 사용합니다. 고정된 스킬 단계나 5단계를 강제하지 않습니다.
명령은 `workId`, 원문 `messageId`, 다음 `plan.revision`을 JSON으로 반환합니다.
단계 전환·막힘·계획 수정 때 반환받은 revision과 같은 messageId로 전체 계획을 갱신합니다.
같은 내용의 재전달은 기존 결과를 반환하고 오래된 revision의 다른 변경은 거부합니다.
원문 메시지를 찾을 수 없으면 등록을 거부합니다. 등록만 하는 명령은 기존 세션에 입력하거나
격리 실행기를 시작하지 않습니다. 실행 인계는 아래 `--execute`를 명시한 경우에만 수행합니다.

상태는 `pending`(대기), `active`(진행 중), `blocked`(막힘, reason 필수),
`reported`(단계 종료 보고)입니다. `passed` 같은 검사 통과 상태를 보고만으로 등록할 수 없습니다.
`evidence`에는 `message:<native-id>`, 파일 위치, 커밋, 실제 검사 결과 위치 등을 연결합니다.
화면에서 원문을 읽을 수 있는 메시지 참조는 내용을 표시하고, 나머지는 확인되지 않은 참조
위치로 표시합니다. 에이전트 보고·참조 위치는 검사기의 검증 근거와 별개입니다.

## 화면과 적용 범위

등록한 계획은 해당 세션의 **실행 흐름**에서 기본으로 표시하며 2초 간격으로 갱신합니다.
실행으로 넘긴 계획은 별도 선택 없이 해당 실행의 실제 상태를 표시합니다.
과거 작업은 **작업 기록**에서 제목·날짜·결과로 찾으며 같은 작업의 이전 실행은 그 안에
접어 표시합니다. **세션 호출 기록**은 작업 기록과 섞지 않고 바로 엽니다.
과거 대화별 LLM 제안은 기본 목록에 넣지 않습니다.
이는 그래프 상태의 갱신 주기이며 native 대화·도구 출력 스트리밍과 별개입니다.
노드를 선택하면 연결한 자료와 막힌 이유를 확인합니다. 과거 작업을 열어도 현재 작업은
계속 갱신되며 **현재 작업으로** 돌아갈 수 있습니다.

Waga가 새로 만드는 Claude·Codex 세션에는 이 등록 절차를 안내합니다. 이는 에이전트가
따를 지침이며 provider의 스킬 호출 이벤트를 강제로 가로채는 훅은 아닙니다.
기존 세션에 지침을 소급 주입하거나 전역 스킬 파일을 수정하지 않습니다.
따라서 이미 열린 세션이나 외부 도구가 계획을 등록하지 않으면 실제 호출 기록만 표시합니다.
그 세션의 스킬 호출이 자동 연결됐다고 주장하지 않습니다.

## 계획을 실제 실행으로 넘기기

수행 에이전트가 사용자가 허용한 로컬 수정·검사 과제를 실행기에 맡길 때는 `execution`을
계획에 포함하고 `waga plan <provider:session-id> <plan.json> --execute`를 호출합니다.
이 명령 이후 원래 에이전트는 같은 파일 수정을 중복 실행하지 않습니다. 실행 결과를
회수하고 후속 사용자 지시를 처리하는 역할을 유지합니다. 별도 상주 관제 LLM은 없습니다.

`execution`은 [실행 명세](web-executions.md)의 형식을 사용합니다. 계획과 같은 단계 ID·제목·
선행 관계를 가지며, 각 단계에 `role`, `prompt`, `outputs`, `inputs`, `check`를 지정합니다.
제공자와 모델은 `execution.providers`, `execution.models`로 명시합니다. 실행 검사 명령은
프로젝트 `package.json`의 test·check·lint 또는 `Cargo.toml`의 `cargo test --jobs 1`에서
확인한 인자 배열을 사용합니다. 검사 자체는 원래 작업의 동작을 검증해야 합니다.
원본 저장소는 커밋된 상태여야 하며 변경은 격리 worktree에 남습니다. 머지·배포나 원본 적용을
자동 실행하지 않습니다.

다음은 실행 단계에 붙이는 조건 예입니다. 선행 `scope` 단계가 `scope.json`을 산출물로
선언하고, 검사와 독립 검토를 통과한 뒤 해당 파일의 해시를 대조하고 JSON을 읽습니다.

```json
{
  "id": "web", "title": "웹 수정", "role": "edit",
  "prompt": "요구된 웹 동작을 수정하세요.",
  "dependsOn": ["scope"], "outputs": ["src/web.mjs"],
  "when": { "from": "scope", "path": "scope.json", "field": "target", "equals": "web" },
  "check": ["npm", "test"]
}
```

`when`의 `path`는 선행 단계의 선언된 산출물이어야 합니다. `field`는 JSON 최상위 필드이고,
`equals`는 문자열·유한수·불리언·null입니다. 조건을 만족하지 않으면 모델을 호출하지 않고
`skipped`로 기록합니다. 일반 선행 관계는 필요한 경로가 제외되면 후속 단계도 제외합니다.
`join: "selected"`인 합류 단계는 모든 선행 경로가 통과 또는 제외된 뒤, 통과한 경로가
하나 이상일 때 시작합니다. 제외된 경로의 산출물은 전달하지 않습니다.

`maxParallel: 2`를 지정해도 의존성·쓰기 충돌·PC 자원 여유를 확인한 작업만 병렬 실행합니다.
같은 입력 파일을 읽는 작업끼리는 병렬로 실행할 수 있습니다. 검사 실패는 해당 작업에만
근거를 전달해 수정하고, 동일 실패가 반복되거나 시도 한도를 넘으면 재계획으로 멈춥니다.
조건 판단의 실제 값·해시, 합류 조건, 검사·검토 결과, 재시도는 실행 그래프에서 확인합니다.
단순히 그림을 복잡하게 만들기 위한 분기나 병렬 작업을 생성하지 않습니다.

동일 계획 revision의 실행 요청을 재전달해도 같은 실행을 반환합니다. 접수 확인이 불명확하면
`waga plan <provider:session-id>`로 저장된 실행을 조회하고 새 실행을 만들지 않습니다.
실행으로 넘긴 계획은 표시용 상태 보고로 덮어쓰지 않습니다. 종료된 실패의 재계획은 위
`replanFrom` 절차를 사용합니다. 일시정지·재개·중단은 웹의
실행 제어를 사용하고, 새로운 요구는 원래 세션의 후속 지시에서 계획합니다.
