# 스킬 실행 계획 연결

계획은 이슈루프처럼 사용자가 시작한 다단계 작업을 수행하는 에이전트가 등록합니다.
수행 에이전트가 이미 작성한 계획을 사용하므로 Waga가 별도 분류·요약 모델을 호출하지 않습니다.
일반 질문·설명·응답 종료는 계획 생성 조건이 아닙니다.

## 에이전트 등록과 갱신

`waga agents --json`에서 자신의 정확한 provider 접두사 세션 ID를 확인합니다.
`waga plan <provider:session-id>`는 최근 원문 사용자 메시지와 기존 계획·revision을 읽습니다.
처음 선택한 원문 ID를 보존하고, 후속 질문마다 새 ID로 계획을 등록하지 않습니다.

에이전트가 다음 형태의 파일을 작성하고 `waga plan <provider:session-id> <plan.json>`으로 등록합니다.
`--cwd`는 선택적인 세션 발견 필터이며 계획 대상은 정확한 세션 ID로 선택합니다.

```json
{
  "messageId": "원래 사용자 지시의 native 메시지 ID",
  "revision": 0,
  "title": "웹·TUI 세션 순서 동기화 수정",
  "skill": "issue-loop",
  "nodes": [
    { "id": "reproduce", "title": "순서 불일치 재현", "dependsOn": [], "state": "active", "evidence": [] },
    { "id": "fix", "title": "저장·조회 경로 수정", "dependsOn": ["reproduce"], "state": "pending", "evidence": [] },
    { "id": "check", "title": "웹·TUI 왕복 동기화 검사", "dependsOn": ["fix"], "state": "pending", "evidence": [] }
  ]
}
```

실제 과제에 필요한 단계와 의존 관계를 사용합니다. 고정된 스킬 단계나 5단계를 강제하지 않습니다.
명령은 `workId`, 원문 `messageId`, 다음 `plan.revision`을 JSON으로 반환합니다.
단계 전환·막힘·계획 수정 때 반환받은 revision과 같은 messageId로 전체 계획을 갱신합니다.
같은 내용의 재전달은 기존 결과를 반환하고 오래된 revision의 다른 변경은 거부합니다.
원문 메시지를 찾을 수 없으면 등록을 거부합니다. 계획 저장은 기존 세션에 입력하거나
격리 실행기를 시작하지 않습니다.

상태는 `pending`(대기), `active`(진행 중), `blocked`(막힘, reason 필수),
`reported`(단계 종료 보고)입니다. `passed` 같은 검사 통과 상태를 보고만으로 등록할 수 없습니다.
`evidence`에는 `message:<native-id>`, 파일 위치, 커밋, 실제 검사 결과 위치 등을 연결합니다.
화면에서 원문을 읽을 수 있는 메시지 참조는 내용을 표시하고, 나머지는 확인되지 않은 참조
위치로 표시합니다. 에이전트 보고·참조 위치는 검사기의 검증 근거와 별개입니다.

## 화면과 적용 범위

등록한 계획은 해당 세션의 **실행 흐름**에서 기본으로 표시하며 2초 간격으로 갱신합니다.
이는 그래프 상태의 갱신 주기이며 native 대화·도구 출력 스트리밍과 별개입니다.
노드를 선택하면 연결한 자료와 막힌 이유를 확인합니다. native 호출 기록과 기존 격리
실행 기록은 같은 탭의 실행 선택에서 확인할 수 있습니다.

Waga가 새로 만드는 Claude·Codex 세션에는 이 등록 절차를 안내합니다. 이는 에이전트가
따를 지침이며 provider의 스킬 호출 이벤트를 강제로 가로채는 훅은 아닙니다.
기존 세션에 지침을 소급 주입하거나 전역 스킬 파일을 수정하지 않습니다.
따라서 이미 열린 세션이나 외부 도구가 계획을 등록하지 않으면 실제 호출 기록만 표시합니다.
그 세션의 스킬 호출이 자동 연결됐다고 주장하지 않습니다.
